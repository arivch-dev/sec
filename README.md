# Secure Gateway: Сервис управления ключами (KMS) и адаптивный балансировщик нагрузки

[![Go Version](https://img.shields.io/badge/Go-1.22%2B-00ADD8?style=flat)](https://golang.org/)

[![Аутентификация](https://img.shields.io/badge/Аутентификация-mTLS%20%2B%20RBAC-blue)](https://github.com/arivch-dev/sec)
[![Мониторинг](https://img.shields.io/badge/Метрики-Prometheus-orange)](https://prometheus.io/)

Монорепозиторий защищенной инфраструктуры на языке Go, настроенный и развернутый в enterprise-окружении Red Hat Enterprise Linux 10.

Проект объединяет два самостоятельных сервиса:
1. Secure KMS (каталог kms) — сервис управления криптографическими ключами. Реализует конвертное шифрование (Envelope Encryption, AES-256-GCM), многоверсионную ротацию мастер-ключей с сохранением на диск, базу данных SQLite в режиме WAL и строгую взаимную аутентификацию mTLS с разделением ролей (RBAC).
2. Adaptive Load Balancer (каталог loadbalancer) — балансировщик нагрузки и reverse-proxy. Поддерживает адаптивное распределение по задержкам бэкендов (EMA Latency), механизм Circuit Breaker (быстрая изоляция сбойных узлов), ограничение частоты запросов (Token Bucket) и экспорт метрик в Prometheus.

## Принцип работы системы

Комплекс построен по многоуровневому принципу и объединяет пограничный уровень распределения сетевой нагрузки и изолированный криптографический контур:

1. Входящий клиентский трафик поступает на порт балансировщика (8080).
2. Балансировщик анализирует пул доступных серверов приложений и динамически направляет запросы на оптимальный узел в соответствии с выбранным алгоритмом: адаптивное распределение по задержкам EMA, наименьшее число соединений (Least-Conn) или циклический опрос (Round-Robin).
3. В адаптивном режиме балансировщик непрерывно рассчитывает экспоненциальное скользящее среднее времени ответа каждого узла, автоматически снижая объем трафика на медленные или перегруженные ноды.
4. При возникновении сбоев срабатывает механизм Circuit Breaker. Если бэкенд фиксирует три последовательные сетевые ошибки, он мгновенно исключается из активной маршрутизации без ожидания планового таймера проверки доступности, предотвращая деградацию сервиса для клиентов.
5. Фоновый воркер балансировщика непрерывно выполняет проверки доступности (health checks) по эндпоинту /health. При успешном восстановлении аварийного узла балансировщик автоматически возвращает его в рабочий пул.
6. Внутренние микросервисы и серверы приложений при необходимости шифрования или расшифровки данных обращаются к сервису Secure KMS по протоколу TLS 1.3 на порт 8443.
7. Сетевое подключение к KMS требует обязательного наличия клиентского сертификата x509, выпущенного доверенным удостоверяющим центром (CA).
8. Сервис KMS валидирует сертификат и определяет роль клиента по полю Common Name (CN): обычные клиенты (client.internal) имеют доступ исключительно к генерации и расшифровке рабочих ключей данных (DEK), а доступ к административной ротации мастер-ключей (KEK) открыт только сертификату администратора (kms-admin). Любые попытки несанкционированного вызова административных методов пресекаются ответом 403 Forbidden.
9. При операции шифрования KMS генерирует одноразовый ключ DEK (AES-256-GCM), шифрует его текущей версией мастер-ключа KEK и возвращает вызывающему сервису. Исходный открытый ключ не сохраняется в открытом виде на диске.
10. Все версии мастер-ключей KEK сохраняются на диске в зашифрованном виде. При проведении плановой ротации мастер-ключа архивные ключи остаются доступными, обеспечивая корректную расшифровку ранее сохраненных данных без необходимости их массовой перешифровки.
11. Каждая криптографическая операция фиксируется в журнале аудита с расчетом контрольной суммы SHA-256, а состояние базы данных поддерживается в SQLite в режиме Write-Ahead Logging (WAL) для предотвращения дедлоков при конкурентном доступе.

## 1. Сервис управления ключами (Secure KMS)

### Криптографическая модель
* Конвертное шифрование (Envelope Encryption):
  Для каждого блока данных генерируется одноразовый ключ шифрования данных (DEK — Data Encryption Key, AES-256-GCM). DEK шифруется мастер-ключом (KEK — Key Encryption Key). Исходный открытый DEK не сохраняется на диске.
* Многоверсионная ротация KEK с сохранением на диск:
  Каждая версия KEK сохраняется в зашифрованном виде на диске (kek.v1.enc, kek.v2.enc и далее). При ротации KEK старые данные остаются доступными для расшифровки через их исходную версию KEK, а все новые операции используют актуальную версию мастер-ключа.
* Взаимный TLS (mTLS) и ролевой доступ (RBAC):
  Все сетевые вызовы защищены протоколом TLS 1.3 с проверкой клиентского сертификата, подписанного внутренним удостоверяющим центром (CA). Роли проверяются по Common Name (CN) сертификата:
  * Обычные клиенты (CN=client.internal) имеют доступ к эндпоинтам генерации и расшифровки данных (/v1/keys/generate, /v1/keys/decrypt).
  * Ротация мастер-ключа (/v1/admin/rotate-master-key) разрешена исключительно сертификатам администратора (CN=kms-admin). Неавторизованным клиентам возвращается 403 Forbidden.
* Хранилище данных и конкурентность:
  База данных SQLite настроена в режиме Write-Ahead Logging (PRAGMA journal_mode = WAL;) с таймаутом ожидания блокировки (busy_timeout = 5000;), что устраняет дедлоки при одновременной записи и чтении.
* Неизменяемый журнал аудита:
  Каждая операция логируется с вычислением контрольной суммы SHA-256, обеспечивая защиту от скрытой модификации истории событий.

## 2. Адаптивный балансировщик нагрузки (Load Balancer)

### Возможности
* Адаптивный алгоритм по задержке (Adaptive EMA):
  Оценивает скользящее экспоненциальное среднее времени ответа каждого бэкенда (LatencyMs = LatencyMs * 0.7 + CurrentReqLatency * 0.3). При возрастании задержки на одном из серверов трафик автоматически перераспределяется на менее нагруженные ноды.
* Предохранитель (Circuit Breaker):
  При возникновении трех последовательных сетевых ошибок бэкенд переводится в статус DOWN без ожидания пятисекундного таймера фонового health check.
* Поддерживаемые алгоритмы:
  * adaptive — взвешенное распределение с учетом времени ответа;
  * leastconn — выбор бэкенда с минимальным числом активных соединений;
  * weighted — статическое взвешенное распределение;
  * roundrobin — классический циклический опрос.
* Фоновые проверки доступности (Health Checks):
  Воркер непрерывно опрашивает эндпоинт /health каждого бэкенда и автоматически возвращает восстановившиеся серверы в рабочий пул.
* Инструментарий наблюдаемости (Observability):
  * Метрики в формате Prometheus на эндпоинте /metrics (число запросов, активные соединения, гистограмма задержек, статус нод).
  * JSON-телеметрия текущего состояния пула бэкендов на эндпоинте /api/backends.

## 3. Развертывание и безопасность в RHEL 10

Сервисы подготовлены для эксплуатации по стандартам информационной безопасности:
* Выделенный непривилегированный пользователь: сервисы запускаются без привилегий суперпользователя root.
* Песочница systemd:
  ```ini
  ProtectSystem=strict
  ProtectHome=yes
  NoNewPrivileges=yes
  PrivateTmp=yes
  PrivateDevices=yes
  ProtectKernelTunables=yes
  ProtectControlGroups=yes
  RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX
  ```
* SELinux: система функционирует в строгом режиме Enforcing. Исполняемым файлам в каталогах /opt/kms и /opt/loadbalancer назначены контексты bin_t, директориям логов и данных — var_log_t.
* Firewalld: открыты целевые порты 8080 (Балансировщик) и 8443 (KMS mTLS).

## 5. Быстрый запуск

### Требования
* Go версии 1.22 или выше
* Утилита OpenSSL
* Linux (RHEL, Rocky Linux, CentOS, Debian, Ubuntu)

### 1. Выпуск сертификатов для mTLS
```bash
chmod +x deploy/generate_certs.sh
./deploy/generate_certs.sh
```

### 2. Сборка и запуск KMS
```bash
cd kms
go build -o kms-server ./cmd/kms
./kms-server --port 8443
```

### 3. Сборка и запуск Балансировщика
```bash
cd loadbalancer
go build -o lb-server main.go
./lb-server --port 8080 --algo adaptive
```

### 4. Проверка состояния и метрик
```bash
curl http://localhost:8080/api/backends
curl http://localhost:8080/metrics
```

## Политика безопасности (Security Policy)
* Закрытые ключи (*.key), зашифрованные файлы данных (*.enc) и базы данных SQLite (*.db) исключены из репозитория через .gitignore во избежание утечки секретов.
* В продуктивной среде мастер-ключи и корневой сертификат удостоверяющего центра (CA) рекомендуется размещать во внешнем аппаратном модуле безопасности (HSM) или защищенном хранилище секретов.
